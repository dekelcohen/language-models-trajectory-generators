# Research Report: Context/Parent-Body Tracking for Occlusion-Robust Door-Handle Tracking

## 1. Classical "supporter"/context tracking (CPU-feasible, directly portable to your pipeline)

- **Tracking the Invisible** (Grabner, Matas, Van Gool, Leibe, CVPR 2010, DOI `10.1109/cvpr.2010.5539819`): learns "supporters" — points *elsewhere* in the scene whose motion is temporally correlated with the target — via Generalized Hough voting, and explicitly estimates target position when it is fully occluded/out of frame. No code released. This is the closest conceptual ancestor of your idea: door-panel/edge/hinge points as Hough voters for handle location even under full handle occlusion.
- **Context Tracker** (Dinh, Vo, Medioni, CVPR 2011, DOI `10.1109/cvpr.2011.5995733`): formalizes "distracters" (suppress look-alikes) vs. "supporters" (keypoints with consistent co-occurrence/motion used to verify re-acquisition). No code; CPU-feasible by design (keypoints + random forest).
- **STC – Spatio-Temporal Context** (Zhang, Zhang, Yang, ECCV 2014, arXiv:1311.1939): FFT-based Bayesian context map between target and surrounding region. **350 fps on an i7 CPU** (author-stated, MATLAB, unoptimized) — official MATLAB code at the [author project page](http://www4.comp.polyu.edu.hk/~cslzhang/STC/STC.htm). Excellent lightweight CPU baseline for "context predicts location."
- **FragTrack** (Adam et al., CVPR 2006) and **Structure-Preserving Tracking** (Zhang & van der Maaten, CVPR 2013, [free PDF](https://lvdmaaten.github.io/publications/papers/CVPR_2013.pdf)): part-based tracking where a "spring"/constellation model lets visible parts constrain occluded ones — directly analogous to a door-panel-patch + handle-patch spring model. Both classical, CPU-feasible.

## 2. Learned point trackers with global context (mostly GPU, but mechanism is instructive)

- **CoTracker / CoTracker3** (Meta, arXiv:2307.07635, arXiv:2410.11831, [repo](https://github.com/facebookresearch/co-tracker)) — code-verified: `cotracker/predictor.py:24,63,147-169` shows a **support grid** of extra query points concatenated to user queries before the joint transformer pass, then sliced off from the output. This proves the "throwaway context points improve a hard point's tracking via joint attention" mechanism works in a shipped SOTA system. GPU-only, no published CPU fps — but the idea (seed meaningful support points, not random grid) is directly reusable even outside CoTracker.
- **TAPIR/BootsTAP** (DeepMind, arXiv:2306.08637 / 2402.00847, [tapnet repo](https://github.com/google-deepmind/tapnet)) ships **TRAJAN**, which explicitly "conditions on a set of support point trajectories and reconstructs... held-out query points" — an existence proof of your exact idea as a learned model. GPU real-time only.
- **LocoTrack** (arXiv:2407.15420) claims near-dense real-time tracking, 6x faster than prior SOTA, but still GPU. **Track-On** (arXiv:2501.18487) uses an online memory module for occlusion recovery (GPU). **PIPs++** (arXiv:2307.15055) and **TAPTR v3** (arXiv:2411.18671, "context-aware cross attention") are GPU, long-horizon-occlusion-oriented.
- **KeepTrack**/**ToMP** (pytracking, arXiv:2103.16556/2203.11192) track distractor candidates explicitly — complements supporter-tracking with "avoid these look-alikes." Note: pytracking's **E.T.Track** (arXiv:2112.09686) is explicitly CPU-real-time-capable — the one genuinely lightweight entry in this family.
- **SAM2/SAMURAI/Cutie** (video object segmentation): mask-level re-identification after occlusion using motion-aware Kalman filters (SAMURAI) over SAM2 masks. All GPU (SAM2: 39–91 fps on A100 only). Useful as a coarse "is the whole door still there, where" signal, not point-accurate, and not CPU-feasible.

## 3. Articulated parent-child kinematic tracking (the most directly relevant family)

- **Martín-Martín & Brock**, "Online interactive perception of articulated objects with multi-level recursive estimation" (IROS 2014) — tracks multiple rigid parts with a **recursive (EKF/particle-filter-like) estimator** fusing a kinematic-structure prior across levels, so occluded/poorly-observed parts are stabilized by better-tracked parts. **This is the single closest precedent to your proposed design** — CPU-feasible, no GPU dependency implied. Companion dataset: [RBO dataset](https://tu-rbo.github.io/articulated-objects/) (arXiv:1806.06465), 14 articulated objects incl. cabinets/drawers with ground-truth part tracks.
- **Sturm et al., "A Probabilistic Framework for Learning Kinematic Models of Articulated Objects"** (JAIR 2011, arXiv:1405.7705): closed-form/least-squares fitting of rigid/prismatic/revolute edge models between two tracked pose trajectories, with BIC model selection; **fully CPU-feasible**, used online on real robots. This gives the exact math for "fit joint type + axis from parent & child pose tracks, then predict child from parent." Companion: Sturm, Konolige et al., "Vision-based detection... of cabinet doors and drawers" (ICRA 2010) — stereo detection of handles feeding this kinematic learner.
- **Yan & Pollefeys** (CVPR 2006 / TPAMI 2008): factorization-based screw-axis/twist estimation from feature trajectories — SVD-based, CPU-feasible, the classical recipe for recovering a revolute joint axis from relative rigid-body motion.
- **DART** (Schmidt, Newcombe, Fox, RSS 2014, [repo](https://github.com/tschmidt23/dart)): GPU/CUDA-only kinematic-chain SDF tracker; architecturally the "parent+child jointly tracked from depth" target but assumes continuous visibility of all links (no explicit occlusion-recovery). Not CPU-feasible.
- **Arduengo, Torras, Sentis**, "Robust and Adaptive Door Operation with a Mobile Robot" (arXiv:1902.09051): CNN handle-grasp detector + online Bayesian kinematic-model inference (hinge vs. sliding, axis location) from observed door motion on a real HSR robot — closest robotics-specific precedent, though no public code.
- **Ditto** (CVPR 2022), **CARTO** (arXiv:2303.15782, ~1Hz on TITAN XP), **ScrewNet** (arXiv:2008.10518), **A-SDF** (arXiv:2104.07645), **OPD** (arXiv:2203.16421), **GAMMA** (arXiv:2309.16264): all single/few-shot *joint-model estimators* from point clouds/images, GPU-only, not continuous trackers — best used offline to calibrate the handle-in-door offset and hinge axis prior, not for live tracking.
- **Gap confirmed by search**: no paper specifically addresses handle tracking occluded by the *robot's own gripper/arm* during manipulation — a genuine niche your work would fill. Nearest supports: Huang, Walker, Birchfield ICRA 2012 (occlusion-aware articulated reconstruction); Klingbeil/Saxena/Ng IROS 2010 (door/handle detection for opening).

## 4. Dense/plane tracking of the door leaf itself (CPU-friendly, strongly recommended core)

- **ESM / IC-LK homography tracking**: classical, CPU-real-time for small templates. Practical implementations: [MTF](https://github.com/abhineet123/MTF) (arXiv:1602.09130) — modular C++/Python/ROS library combining ESM/IC/RANSAC search methods with SSD/NCC appearance models and homography/affine state spaces; [libcvd](https://github.com/edrosten/libcvd) (`cvd/esm.h`). Treats the door panel as a textured plane, recovering full projective pose per frame from RGB alone.
- **Point-to-plane ICP / Generalized-ICP** on depth: the best-fit *geometric* primitive for your case — a door leaf is large and near-planar, so point-to-plane ICP against a few thousand depth points is robust to handle-sized occlusion (outlier/missing region is small relative to the plane). CPU-real-time (sub-10ms/frame typical for ~1-5k points). [Open3D](http://www.open3d.org/docs/release/tutorial/pipelines/icp_registration.html) ships this out of the box; reference GICP implementation: [avsegal/gicp](https://github.com/avsegal/gicp) (Segal, Haehnel, Thrun, RSS 2009).
- **Kabsch/Procrustes+RANSAC**: standard, CPU-trivial — Open3D's `registration_ransac_based_on_feature_matching`, or `scipy.spatial.transform.Rotation.align_vectors`/`scipy.linalg.orthogonal_procrustes` for the closed-form step. Confirms your current pose_tracker approach generalizes directly to a larger point set on the door.
- **POT-210 benchmark** (arXiv:1703.07938) and follow-up **WOFT** ([repo](https://github.com/serycjon/WOFT), WACV 2023) are good validation targets for occlusion/out-of-view robustness of whichever planar tracker you pick.

## Recommended Implementation Design

**Core idea**: treat the door leaf as a second, larger `TrackingTarget` ("parent") tracked by the *same* pose_tracker machinery you already have, with the handle as a "child" expressed in the parent's frame plus one extra latch-rotation DoF. This reuses your Kabsch+Kalman infrastructure and needs no deep nets, matching Martín-Martín & Brock's recursive multi-level estimation and Sturm et al.'s kinematic-edge-fitting pattern.

**(a) Context/supporter points on the parent.** From the VLM-given door mask (or a RANSAC plane fit on depth restricted to the door's bounding region), seed 15–30 NCC-tracked points spread over the visible door panel/edges/frame (avoid the handle's local neighborhood) per camera — same 11×11 NCC machinery you already have, just more points and spatially distributed so a handle-sized occluder (robot arm/disc) can never cover more than a few. This is the STC/Context-Tracker idea implemented with your existing primitives.

**(b) Parent-pose estimation.** Lift supporter points to 3D via depth each frame; fit a rigid transform with Kabsch+RANSAC (reuse your fusion code) for the door leaf's pose. Because the door is planar and large, optionally add point-to-plane ICP (Open3D, CPU, <10ms for ~1-5k depth pixels in the door's masked region) as a second, denser pose source to fuse/cross-validate against the sparse-point Kabsch fit — this directly handles the case where NCC supporter points individually drift but the plane geometry stays constrained. Run this parent pose through its own rigid-body Kalman filter (mirroring your existing green/yellow/red/black health state machine, since the door is itself non-rigid relative to the room — it's an articulated joint, not fully rigid — but rigid+1-DoF is a good local linearization).

**(c) Child prediction = T_parent · T_child_in_parent(θ).** Calibrate `T_child_in_parent` once when both door and handle are cleanly visible (first few frames, or whenever health=green on both): compute the handle's pose relative to the fitted door-plane frame. Model the handle as having one extra unknown, the **latch rotation angle θ** (lever rotating about its own small axis, independent of door hinge rotation) — track θ as a 1D state in the handle's own Kalman filter, predicted via constant-velocity/acceleration in θ, updated by whatever handle points remain visible.

**(d) Learning the hinge axis online.** While both door-parent and room-frame poses are being tracked over several frames of door motion, fit the hinge's screw axis via the Sturm et al. JAIR least-squares/EM approach (closed-form SVD per Yan & Pollefeys, or simple Gauss-Newton on consecutive parent SE(3) poses) — this gives you `T_door_in_room(φ)` parametrized by hinge angle φ, letting you sanity-check/constrain the parent pose estimate itself (reduces its DoF from 6 to 1, hugely increasing robustness if the door's own panel is briefly degraded) and separately recover during combined door+arm occlusion by extrapolating φ from its own motion model.

**(e) Fusion into re-acquisition.** When the handle's local NCC/patch-bank health goes red/black, do **not** run a wide-image RANSAC search blind: first compute the predicted handle pixel location in each camera from the current (green/yellow) parent pose and T_child_in_parent(θ̂), and only run your existing patch-bank + NCC + RANSAC re-acquisition inside a tight window (e.g., ±15–20 px) around that prediction. This converts re-acquisition from "search everywhere, hope the rotated patch bank still matches" into "verify a strong prior," which should directly fix the lever-rotation/foreshortening drift failure you described. If the parent's own health is also red (fully occluded), fall back to constant-velocity extrapolation of the full parent+child joint state from the kinematic model (hinge angle φ and latch angle θ), same as your Kalman filter already does for short gaps, just at a coarser hierarchical level.

**(f) Failure modes to design for.**
- *Parent occluded too* (e.g., arm swings in front of the whole door): fall back to room-frame hinge-angle extrapolation (pure kinematic prediction, no visual update) for a bounded time budget before flagging black/lost — same timeout logic as today but at the door level.
- *Child moves relative to parent beyond the modeled DoF* (lever rotates about an axis not aligned with your assumed 1-DoF model, or for a grasped box sliding on a table — parent="table surface", child="box", relative motion could be a full 6-DoF slide): make `T_child_in_parent` adaptive — re-estimate it via a sliding-window least-squares fit (Sturm-style) whenever both are well-tracked, rather than freezing it at calibration; detect divergence (prediction-vs-NCC residual growing) and widen the search window / increase process noise in the child's own KF rather than trusting the parent prediction blindly.
- *VLM mask quality for the parent*: if the door mask is noisy/partial, fall back to RANSAC plane-fit segmentation of the depth image in the door's rough bounding region (don't require a pixel-perfect VLM mask — just a seed region).
- *Box/table case generalizes directly*: grasped box ↔ gripper-parent (rigid, known via FK) rather than box ↔ table-parent (if the box is placed on the table, treat the table as parent with a prismatic+planar constraint instead of revolute).

## User follow-up angle

Additional angle from the user to cover in the report: global context as UNIQUENESS / distinctiveness, not just motion. Example: along a line through the door there is "gray back-latch -> brown door band -> gray handle". Locally the handle patch (gray blob) is ambiguous and changes with rotation, but the larger-scale layout pattern (sequence/constellation of coarse parts with relative geometry) is unique in the scene, so after occlusion any location where this coarse pattern appears is the match. Please research: multi-scale / context descriptors for re-detection (e.g. shape context, DAISY / large-support descriptors, coarse-to-fine/pyramid template matching with masked large templates, "contextual descriptors" for keypoint disambiguation, constellation / pictorial-structures / deformable part models with star geometry, generalized Hough voting from context features (implicit shape model, ISM), "local-global" matching, RANSAC over part constellations, color-layout descriptors, attention-based matchers like LoFTR/LightGlue/SuperGlue that use global context to disambiguate repetitive local features, and segment-level matching (SAM masks + relation graphs). Recommend a CPU-friendly implementation for our pipeline: e.g. a coarse context template/descriptor captured at seed time over a larger region (object + surroundings, with the moving part masked or down-weighted), matched at low resolution to get a unique coarse location, then local refinement; and a constellation of context points on the parent body voting for the child location. Include failure modes (context changes as the door swings: perspective; arm occluding context).


# Addendum: Global Context as UNIQUENESS/Distinctiveness (not motion) for Re-Detection

This covers the "coarse layout is unique even though the local patch is ambiguous" angle — e.g., gray-latch → brown-band → gray-handle is a locally-ambiguous but globally-unique constellation.

## A. Classical descriptors/models for coarse-context uniqueness

| Approach | Summary | Links | CPU/real-time | Relevance |
|---|---|---|---|---|

| **DAISY** (Tola, Lepetit, Fua, PAMI 2010, DOI `10.1109/TPAMI.2009.77`) | Dense, large-support circular gradient-ring descriptor, bigger spatial support than SIFT, built for dense wide-baseline matching. | [libdaisy](https://github.com/etola/libdaisy); also `skimage.feature.daisy`, OpenCV `xfeatures2d::DAISY` | Very high — "200-length descriptors/pixel on 800×600 in <5s" (2009 HW); trivially real-time per-ROI today | Compute at coarse scale over the handle's wider neighborhood (not just the blob) for a rotation-tolerant context signature |

## Recommended CPU-friendly design addition

Add a **distinctiveness-based re-acquisition path** that runs alongside (not instead of) the parent-kinematic prediction from the previous report — use whichever gives a tighter/more confident candidate:

1. **Capture a coarse context template at seed time.** When the VLM gives the affordance pixel (and ideally a door/parent mask), crop a generously larger region around the handle (e.g., 4-8× the handle's size) at the seed frame, downsample it (e.g., to 16-32px per side), and **mask or down-weight the handle's own ambiguous blob** (and any known occluder footprint) — keeping the latch/band/edge pixels that give the pattern its uniqueness. Store this as a small masked low-res template (cheap: `cv2.matchTemplate` with `mask`) plus optionally a coarse color-layout vector (MPEG-7-CLD-style, 8×8 grid) as a fast pre-filter.
2. **Coarse re-acquisition scan.** On occlusion/health=red, run masked NCC (or the CLD vector) of this coarse template at low resolution over the full frame (or a generously widened window, wider than the local patch-bank search) — this is sub-millisecond and finds the unique "latch→band→handle" region even when the fine handle appearance itself has rotated/foreshortened beyond patch-bank recognition.
3. **Constellation/verification refinement.** Represent latch, band-segment, and handle as 3 nodes of a simple chain pictorial structure (Felzenszwalb-Huttenlocher-style, or just a direct relative-offset check) with expected relative offsets/angles (calibrated at seed time, updated as the door rotates using the parent pose from the kinematic-prediction path in the main report). Score candidate coarse-match locations by how well the 3-part relative geometry agrees, then RANSAC/consistency-check against the parent-pose-predicted location if available — the two re-acquisition signals (context-uniqueness and kinematic-prediction) should agree; if they disagree, prefer the kinematic prediction but widen the search for next frame.
4. **Local fine refinement.** Once the coarse unique location is confirmed, run your existing 11×11 NCC/patch-bank matching in a tight window around it to recover sub-pixel precision, same as today.
5. **Optional GPU plug-in.** If a GPU becomes available, LightGlue (concrete CPU number too: 20fps@512kp on i7) or LoFTR/EfficientLoFTR can replace step 2-3 wholesale, matching a stored keyframe crop against the live frame with genuine learned global attention instead of hand-crafted masked-template + pictorial structure — same coarse→fine role, better invariance to lighting/perspective, at the cost of GPU dependency.

**Failure modes specific to this uniqueness-based path:**
- **Context itself changes with viewpoint** as the door swings (perspective foreshortening of the band, lighting change) — mitigate by periodically **re-capturing/updating the coarse template** whenever health is green (not just once at seed time), and/or warping the stored template by the door's currently-estimated pose (from the parent-tracking Kalman filter in the main report) before matching, so the coarse NCC/pictorial-structure comparison is pose-normalized rather than raw-pixel.
- **Arm occludes the context region too**, not just the handle — since the coarse template covers a larger area than the local patch, a large occluder can still defeat it; always keep this as a secondary/complementary signal to the kinematic-prediction path (Section on parent/hinge tracking), falling back to pure motion-model extrapolation when both the local patch and the coarse context are occluded.
- **Repetitive context** (e.g., two visually similar handles/doors in frame) could make the coarse match itself ambiguous — this is exactly the "perceptual aliasing" problem from the SLAM literature (DC-GM, Early Bird); resolve with the RANSAC/constellation consistency check against the kinematic prior, which most repetitive-but-wrong candidates won't satisfy simultaneously.
